# T4: 오프라인 캐시·제한 재시도 계약

상태: 오프라인 구현. 실제 API 호출, 비용 발생, 자동 게시 연결은 하지 않았다.

## 변경 전 검증과 범위

새 `test_translation_execution.py`를 먼저 작성해 실행 계층 모듈이 없는 상태에서 수집 실패를 확인했다. 이어 새 `translation_execution.py`로 T1의 요청·검증 결과와 T2의 단일 호출 어댑터를 재사용했다. 기존 제공자 호출·발행 경로는 수정하지 않는다.

## 캐시

`TranslationCache`는 호출자가 명시적으로 만드는 프로세스 메모리 저장소다. 저장 값은 T2와 T1 검증을 통과한 `TranslationResult`뿐이다. provider 요청, 헤더, 키, 원문, 실패 응답을 저장하지 않는다. 별도 파일이나 DB를 생성하지 않는다.

키는 canonical URL, 원문 해시, 규칙 버전, 명시적 제공자와 모델의 JSON을 SHA-256으로 해시한 값이다. 원문 해시는 article ID·canonical URL·제목·요약·출처·발행 시각·protected_terms 전체를 포함한다. 자격 증명은 키에 넣지 않는다. 자격 증명을 교체해도 동일 검증 결과를 재사용하지만 선택 제공자의 키가 없으면 캐시 적중보다 먼저 구성 실패로 종료한다.

TTL은 주입된 동일 monotonic 시계 기준으로 동작한다. 만료된 해당 키는 조회 시 삭제하고 새 호출을 수행한다. 시계가 저장 시점보다 과거라면 해당 캐시 항목을 폐기한다. 무제한 서비스용 저장소가 아니므로 운영 연결 시 기사 배치별 수명과 메모리 상한을 따로 정해야 한다. 다른 프로세스와 공유하지 않으며 재시작 시 캐시는 사라진다.

## 재시도와 예산

- 실행당 시도 상한: 기본 3회, 허용 1~5회.
- 실행 경과 상한: 기본 60초, 허용 최대 600초.
- 시도별 timeout: 기본 30초, 최대 120초이며 남은 실행 예산보다 길게 전달하지 않는다.
- delay: 기본 1초, 기본 cap 8초. `min(cap, base * 2^(attempt-1)) * (0.5 + jitter/2)`를 적용하며 jitter는 주입 함수의 0~1 값이다.
- 429·5xx·timeout 등의 `ProviderError.retryable=True`에만 같은 제공자·모델로 재시도한다.
- 인증·요청 오류·출력 구조/사실 검증 실패·키/모델 구성 오류는 재시도하지 않는다. 다른 제공자로 전환하지 않는다.
- 각 시도 전 경과 시간과 시도 수를 확인한다. 예정 sleep이 남은 시간을 소진하면 sleep도 다음 요청도 하지 않는다. sleep이 과하게 지연됐으면 다음 루프에서 추가 요청을 차단한다.
- 성공이 실행 마감 이후에 돌아오면 결과를 반환하거나 캐시하지 않는다.

동기식 Python은 임의의 주입 transport 실행을 강제로 중단하지 못한다. 실제 transport는 전달받은 timeout을 지켜야 한다. 이 계층은 일일 비용·사용자 전체 호출·토큰 사용량 예산을 보장하지 않는다. 토큰 상한은 현재 T2 요청 값을 사용하며 운영 비용·모델 가용성 검증은 별도다.

## 검증

T4 테스트 45개를 결정적 fake transport·clock·sleeper·jitter로 실행했다. 캐시 적중 시 0개 추가 호출, 모든 원문/규칙/제공자/모델 변경, TTL 경계, 키 교체, 키 누락, 429·5xx·built-in/requests timeout, 401·403·400·출력 실패, backoff/cap/jitter, 최대 시도, 시간 예산, 지연 sleep, 잘못된 구성, 역행 시계를 검사한다. 테스트는 requests 전송을 차단한다.

캐시 키와 repr에 비밀이 노출되지 않는지 확인한다. 이 모듈은 로그를 쓰지 않는다. API 호출·재시도 승인 또는 자동 발행 성공을 뜻하는 검증은 아니다.
